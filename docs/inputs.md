# Inputs & prerequisites

A GESPO run needs three things. Only the first two are yours to supply — the third
(seed trajectories) is produced by `gespo seed`.

## 1. A prepared structure (PDB)

The `--pdb` you pass to `pretrain`, `seed`, and `train`.

- **Explicit solvent** (proteins in a water box, all protein–ligand work): a fully
  solvated, equilibrated PDB (protein + ligand + water + ions). GESPO strips and
  re-solvates a fresh box internally, so a previously-solvated PDB is fine.
- **Implicit solvent** (small proteins, e.g. Trp-cage): a hydrogen-added,
  protein-only PDB. No water/box needed.
- **Protein–ligand**: the ligand must be present as a residue (commonly `BEN`,
  `LIG`, or `UNK`). GESPO parameterizes it from `--ligand-smiles` at runtime
  (GAFF-2.11), so no ligand `.prmtop`/`.mol2`/`.xml` is required. See
  [`ligands.md`](ligands.md).

There is **no bundled/default structure** — `gespo train` errors clearly if `--pdb`
(or `endpoints.pdb_a` in YAML) is missing.

## 2. The geom2vec package + a backbone checkpoint

The `geom2vec_vamp` projection embeds each frame with a pretrained **geom2vec**
representation model. geom2vec is a **separate package** — GESPO does not vendor it
and does not list it in `install_requires`, so you install it alongside GESPO.

**Install the package.** Clone and `pip install -e .` (it needs the PyTorch
Geometric stack — follow the PyG install notes for your CUDA/torch build):

```bash
git clone https://github.com/zpengmei/geom2vec.git
cd geom2vec
pip install -e .            # or:  pip install -e .[torch,pyg,optim]
```

**How GESPO finds it.** GESPO uses a pip-installed `geom2vec` if importable;
otherwise it searches, in order: `$GEOM2VEC_SRC`, an `apps/geom2vec/src` checkout
next to the GESPO repo, then `/project/dinner/*/apps/geom2vec/src`. If you did not
`pip install`, point GESPO at the checkout:

```bash
export GEOM2VEC_SRC=/path/to/geom2vec/src
```

**Get a checkpoint.** The geom2vec repo **ships** pretrained backbones in its
`checkpoints/` folder — no training required. The examples use
`tensornet_l3_h64_rbf32_r5.pth` (TensorNet, 3 layers, hidden 64, 32 RBFs, 5 Å
cutoff).

**Auto-detection.** For `--projection geom2vec_vamp`, GESPO **auto-detects** a
checkpoint if you don't pass `--geom2vec-ckpt`. It resolves, in order:
`$GEOM2VEC_CKPT` → `<prefer>.pth` in a known checkpoints dir → any `tensornet_*.pth`
→ any `*.pth`, searching `$GEOM2VEC_SRC/../checkpoints`, the pip-installed geom2vec
package's `checkpoints/`, and an `apps/geom2vec/checkpoints` checkout near the repo.
The run logs the choice (`[Preflight] Auto-detected geom2vec checkpoint: …`). To
pin one explicitly:

```bash
export GEOM2VEC_CKPT=/path/to/geom2vec/checkpoints/tensornet_l3_h64_rbf32_r5.pth
# or per-run:  --geom2vec-ckpt <path>   (a bare filename is resolved against the known dirs)
```

GESPO reads the architecture from the checkpoint **filename**
(`create_model_from_checkpoint`), so keep the descriptive name. To use a different
architecture or train your own, see the geom2vec repo and
[`../gespo/projections/geom2vec/README.md`](../gespo/projections/geom2vec/README.md).

## 3. Seed trajectories (produced by `gespo seed`)

Short biased/high-T MD that gives the policy a diverse starting ensemble and forms
the replay pool. Generated by `gespo seed` — see [`seeding.md`](seeding.md). The
standard layout is:

```
seeds/
  walker_1/simulation_topology.pdb
  walker_1/production.dcd
  walker_2/simulation_topology.pdb
  walker_2/production.dcd
  ...
```

which is consumed directly by:
- `gespo pretrain --source seeds/walker_1,seeds/walker_2,...`
- `gespo train --replay-only-dcd-dir seeds/walker_1,seeds/walker_2,...`

`--source`/`--replay-only-dcd-dir` accept a comma-separated list of directories (or
a single directory searched recursively for DCDs).

Keep each walker's `simulation_topology.pdb` beside its DCD: seed generation
can change the solvent atom count and ordering. High-temperature restarts also
require this saved topology and reuse it instead of re-solvating the system.

## Between rounds: `simulation_topology.pdb`

On the first run, GESPO builds the solvated system and writes
`<snapshot_dir>/simulation_topology.pdb` (the exact atoms/ordering of the simulated
system). In multi-round protocols, **copy this file forward** to the next round's
snapshot dir so the system is identical across rounds (the example
`04_train_r2.sh` does this). The re-pretrain step in later rounds should also point
`--pdb` at the same topology so torsion indexing matches.

## Environment

- Python with **OpenMM** (+ `openmmforcefields` and the OpenFF toolkit for ligand
  GAFF parameterization) and **mdtraj**, plus **torch** for the policy/VAMP models.
- A CUDA GPU (`--platform CUDA`, `--gen-device cuda:0`). Multi-GPU rollouts:
  `--enable-multi-gpu`. Seed fan-out uses one GPU per walker (`--device cuda:0,cuda:1,...`).
- `import gespo` itself is cheap — the heavy stack loads only when you actually run
  a command.
